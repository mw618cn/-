# 代码逐段导读：从参数到模型，再到24小时图形

本文件解释代码为什么这样组织、每一块解决什么问题、如何把输出追溯到输入。建议先运行交付的示例，再按本文件顺序阅读源码。每个模块的中文docstring和分段注释与这里的解释相互对应。

## 0. 整条计算链

```text
配置JSON + 默认参数
        ↓ config：合并、单位/时间网格/概率校验，生成负荷与PV
四个隐含损伤情景 + 八个因果队伍策略
        ↓ crew：生成物理任务线、已观察历史、线路修复可用性
逐个策略 × 启动/等待/自由分支
        ↓ model：变量、费用、SOC、启动、网络、条件非预期性
稀疏MILP
        ↓ linear：HiGHS求解，保留可行上界和对偶下界
候选解
        ├→ validation：线性约束、边界、整数性、独立物理检查
        ├→ solution：有单位的时序、韧性指标、费用与求解状态
        ├→ capability：固定离散方案→全24h LP投影→完整轨迹分解
        └→ plotting：24h轨迹、韧性面积、启动、巡检、条件域与D值
JSON / CSV / PNG / SVG / PDF
        ↓ scripts/build_paper.py
模型与算例Word（可编辑OMML公式）+ LaTeX公式源
```

重要下标：`s`为损伤情景，默认4个；`m`为微网，默认3个；`i`为节点，默认6个；`e`为支路，默认6条；`t`为15分钟调度区间，默认96个。`energy[..., t]`是区间起点能量，所以其最后一维长度是97。程序内部所有物理量使用MW、Mvar、MWh、小时；费用使用千元。

## 1. config.py：把假设变成可追溯参数

### 1.1 `default_config()`：单一默认参数入口

这个函数返回字典，不立即建模或求解。每次调用都生成新字典，避免不同实验意外共享修改后的参数。其字段按物理角色分组。

| 参数组 | 主要字段 | 含义与后续使用 |
|---|---|---|
| 时间 | `horizon_hours`、`step_minutes` | 决定24小时、96区间；被曲线、SOC、维修、启动和费用共同使用 |
| 初始主网 | `alpha`、`grid_reference_mw` | 外部初始可用注入上限；默认alpha=0，不代表目标机组从模型消失 |
| 网络 | `nodes`、`edges`、`base_mva`、电压/多边形参数 | 节点映射、支路容量、LinDistFlow电压与无功约束 |
| 微网 | `microgrids`的三组设备字典 | 各微网储能、PV、常规电源、逆变器和费用 |
| 负荷 | `critical_base_mw`、`general_base_mw`、`power_factor` | 六节点负荷需求及无功需求；关键/一般恢复损失区分 |
| 机组 | `generator` | 连续启动辅助功率、启动时窗、在线容量与爬坡 |
| 队伍 | `crew` | depot/A/B旅行时间、巡检耗时、轻/重损维修耗时 |
| 情景 | `scenarios` | 联合损伤类型及概率，不是预先向调度器公开的真值 |
| 求解 | `solver` | 时限、相对间隙、预处理等HiGHS选项 |

例如MG1额定能量2.6MWh、初始SOC0.70，对应初始能量1.82MWh；末端SOC0.30对应至少0.78MWh储备。这个末端约束会改变是否值得早启动，所有对照实验必须一致。

默认机组启动轮廓为4个15分钟阶段，辅助有功分别0.45、0.75、0.55、0.25MW。它表示1小时连续支撑需求，不能用“平均0.5MW”替代阶段约束。默认启动候选间隔请以解析后的配置为准，可以改成30分钟或15分钟，但候选时间必须与调度步长对齐。

### 1.2 `_merge(base, patch)`：配置覆盖规则

字典递归合并，列表整体替换。这样只写 `{"alpha": 0.2}` 就能改变初始支撑比例而保留其他默认值；若覆盖 `microgrids` 或 `scenarios`，则应提供完整列表。理解列表整体替换很重要：只写一个微网并不表示修改第一个微网，而是把全部微网列表替成一个元素，随后规模校验会失败。

### 1.3 `load_config(path=None, overrides=None)`：合并并校验

顺序为：默认值→可选JSON→可选程序覆盖→计算 `n_steps`→校验。该函数不是简单读文件。

- 检查时域能否被步长整除，防止96时段之外多出半个时段。
- 检查当前原型固定的6节点、6支路、3微网规模；扩容须同步改节点映射与物理约束。
- 检查alpha处于0—1，概率严格为正且和为1。
- 检查SOC初值、上下界和末端要求，容量/功率/效率为正且效率不超过1。
- 检查模式和启动控制周期是调度周期整数倍，巡检维修时间与网格对齐。
- 检查辅助功率分段不会被粗时间网格跳过、功率因数合法、旅行时间与网格对齐、情景ID唯一。

输入错误应在这里尽早失败，而不是交给求解器产生难以理解的不可行状态。

### 1.4 `build_profiles(cfg)`：生成物理需求，不生成恢复结果

先计算区间起点 `time = arange(n)*dt`，再用区间中点生成负荷和PV。负荷需求有白天和晚间形状，关键负荷波动较小。PV使用6—18时的非负正弦形状乘各微网装机峰值。它们都是**给定预测需求/可用资源**，真正恢复多少由模型决定。

`elapsed = 1 + elapsed_cost_growth * midpoint`让灾后越晚仍未恢复的电量损失权重更高。这是随全局灾后时间变化的权重，**不是**逐负荷累计中断时长的状态模型。若论文要研究内生停电持续时间损失，需要另增负荷中断状态和相应损失函数。

返回的 `critical_voll`、`general_voll`单位千元/MWh，乘未供电MW和 `dt`小时得到费用。`grid_price`同样按电量计费。

如配置中提供 `profiles`，相应显式数组会覆盖示例生成曲线。覆盖项包括 `pv_mw(3,N)`、`load_critical_mw(6,N)`、`load_general_mw(6,N)`和三个一维费用曲线 `grid_price/critical_voll/general_voll(N)`，必须形状正确、有限且非负。这样后续真实时序可以只换JSON而不改优化模型。`scripts/import_profiles.py`把96行CSV转为这种配置，详见数据替换指南。

## 2. crew.py：损伤、观测与维修不是一件事

### 2.1 `build_scenarios(cfg)`：联合损伤情景

函数深复制配置的情景列表。默认情景LL/LH/HL/HH分别是A轻B轻、A轻B重、A重B轻、A重B重；概率分别0.36、0.24、0.24、0.16。复制是为了防止某次实验修改观测或任务后污染其他实验。

情景的 `damage`是生成物理结果的隐含真值。调度模型不能在t=0直接用这个标签选择不同功率；它必须受到后面的条件非预期性约束限制。

### 2.2 `enumerate_policies(cfg)`：八种可执行的因果策略

候选由三个选择构成：先巡A还是B；先巡地点为轻伤时先修它还是先去另一点；先巡地点为重伤时先修它还是先去另一点。因此总数为 `2 × 2 × 2 = 8`。

例如策略ID `A_10` 表示先巡A，A轻则先修A，A重则先去B。这里“轻/重分支”只能在A巡检完成后使用，不能在出发时就知道。策略不是一条固定场景路径，而是一张小的决策规则表。

这里穷举的是声明的8个策略，不是优化任意车辆路径。把有限策略集扩充得更丰富，会扩大可行策略集并可能改善目标；若要求连续路由、等待和多队伍协作，应建立新的路由/调度模型，而非把本枚举结果称为一般VRP最优。

### 2.3 `schedule_policy(cfg, policy, scenarios)`：展开任务与信息

函数对同一策略在每个隐含情景下生成任务线。三个内部小函数分别负责：

| 内部函数 | 改变的状态 | 物理含义 |
|---|---|---|
| `travel(site)` | 时钟与队伍位置 | 队伍不能同时在A/B，旅行期间不能检修 |
| `inspect(site)` | 时钟、该点巡检结束时刻 | 只有结束后知道该点损伤类型 |
| `repair(site)` | 时钟、该点维修结束时刻 | 使用真实损伤条件下的工时，开始后不可中断 |

若先修本点，任务为“出发→巡检1→维修1→旅行→巡检2→维修2”；若先去另一点，任务为“出发→巡检1→旅行→巡检2→维修2→返回→维修1”。策略决策只依赖已经完成的首个巡检结果。

返回的 `inspection_hours`与 `repair_hours`分别是信息出现与线路可用时刻，不能混用。`availability[site][t]=1`表示该线路已经修好，可以由电力模型决定是否合闸，而非必须立刻合闸。

用默认参数展开 `A_10` 的实际时间如下，单位h。这些数由队伍代码计算，不是手工指定给优化器的启动时刻。

| 隐含情景 | A巡检结束 | B巡检结束 | A修复结束 | B修复结束 |
|---|---:|---:|---:|---:|
| LL | 1.0 | 3.0 | 2.0 | 4.5 |
| LH | 1.0 | 3.0 | 2.0 | 8.0 |
| HL | 1.0 | 2.0 | 8.0 | 3.5 |
| HH | 1.0 | 2.0 | 11.5 | 7.0 |

在0—1h，四情景控制都必须一致；1h后可按A轻/重分两组；A重的两个情景在2h已知道B，A轻的两个情景要到3h才知道B。因此不同分支的信息揭示时刻不同，不能用固定“第2小时全部知道损伤”代替。

### 2.4 `observation_history_by_step`：条件非预期性的依据

对每个t，仅收集 `inspection_end <= t` 的观测，内容包含地点、已知损伤、观测时刻。还没巡检完成时历史为空；完成A后，A轻的两个情景形成一组、A重的两个情景形成另一组；B也完成后才可完全区分。

模型比较的是**当前时刻已知历史**是否相同，不是直接比较情景编号。相同历史的场景当前控制必须一致。由此排除“还未看到B重伤，就已经按B重伤安排储能”的未来信息泄漏。

队伍任务不可中断通过物理任务日程保证，非预期性通过历史等价类保证。它们分别解决执行锁定与信息可用性，不能互相替代。

## 3. linear.py：把研究模型变成求解器能读的矩阵

### 3.1 `LinearModel`：统一数学形式

全部模型写成：

```text
minimize      cᵀ x + objective_constant
subject to    row_lb ≤ A x ≤ row_ub
              lb ≤ x ≤ ub
              x_j为连续或整数（由integrality指出）
```

`var_indices`把物理变量名称映射到x的列号，`metadata`保存情景、曲线、策略与系数。模型本身用稀疏CSR矩阵，不是密集数组；96时段×4情景的约束绝大多数系数为零，稀疏结构显著降低内存。

### 3.2 `ModelBuilder.add_var(...)`：先按物理形状登记变量

例如 `(4,3,96)`的储能放电块对应1152个列号。函数把标量或可广播数组的上下界/费用展开，与同形列号一起返回。后续写 `discharge[s,m,t]` 即可得到对应全局列，不需要手工估算偏移。

`integer=True`且上下界0—1才表示二进制。某变量的费用包含概率和时长时，应在建模时正确广播；变量自身仍有MW等物理单位。

### 3.3 `ModelBuilder.add_row(coeff, lb, ub, name)`：逐条构造约束

`coeff`为“列号→系数”字典。等式用 `lb=ub`；上界不等式只设置ub；下界只设置lb。函数记录行名、行上下界和非零系数，便于校核时定位哪一类约束有残差。

例如储能能量守恒的系数为 `+E[t+1] − E[t] − dt*eta_c*charge[t] + dt/eta_d*discharge[t] = 0`。同一物理量不要以错误单位重复缩放，尤其注意充放电效率的位置不同。

### 3.4 `ModelBuilder.build()`：一次组装CSR

先通过COO行/列/值列表收集系数，再转换成CSR。这样建模循环只追加非零项，避免每次加一条约束都复制大矩阵。最终同时保留有名变量索引和约束名称。

### 3.5 `solve(model, solver_cfg)`：MILP求解与上下界

SciPy的 `milp`调用HiGHS，读入目标、整数标记、变量界和稀疏约束。返回：

| 字段 | 含义 |
|---|---|
| `x` | 找到的可行候选解；没有候选时为None |
| `objective` | 候选解代价，含停电损失常数项，是最小化问题的可行上界 |
| `lower_bound` | 求解器对最优值的下界，不能当作可行方案 |
| `status`、`message` | 达到设定最优性容差、时限、不可行等状态 |
| `mip_gap` | 求解器对不含目标常数部分报告的原始相对间隙 |
| `absolute_objective_gap` | 含停电常数后真实费用的上界减下界，单位千元 |
| `relative_objective_gap_including_constant` | 上述费用绝对间隙除以含常数的候选费用绝对值 |
| `solve_seconds` | 实际求解耗时 |

时限结束但有x，可继续检查其可行性并出图；这不表示已证明最优。若无x，应保存失败状态而跳过物理结论与曲线，不能用全零数组冒充恢复方案。

本模型用“全部失供损失常数−已恢复价值”写目标，求解器内部的非恒定目标可能是一个绝对值很大的负数。原始 `mip_gap`的分母因此与最终正的恢复费用不同：原始间隙很小，不代表最终费用也有相同相对精度。解释结果应同时看真实费用上/下界、含常数绝对/相对间隙和D区间。

### 3.6 `freeze_discrete(model, x)`：从已选方案得到条件连续模型

先检查x中的整数值误差；通过后，把整数列的上下界都固定到四舍五入的取值，并将整数标记清零。SOC、网络、负荷、启动轮廓和信息约束均保留。

这得到当前启动/开关/模式方案条件下的LP。它不是把原MILP整体变凸，也不包含其他离散方案。能力域图与任何后续ADMM收敛说明都只能在这一条件范围下解释。

### 3.7 `solve_lp(model, objective=None, extra_equalities=None)`：投影与分解共用接口

将双边约束拆成等式与上下界不等式，调用 `linprog(method='highs')`。若提供新目标，就用它求支持方向；若不提供，仍优化原运行费用。新增等式以 `({列号:系数}, 右端值)` 列表传入，能力分解时用于固定整条主配接口轨迹。

## 4. model.py：把三个研究问题落成同一套约束

核心入口为 `build_model(cfg, policy, branch='free', information='causal', coordination=True, ...)`。它只建立模型，不产生最优解；求解器调用在后续模块中完成。这样同一物理模型可在不同策略、条件动作和信息假设下复用。

源码中01—09编号块依次为：读取曲线/情景；建立三种动作网格及启动系数；登记变量与费用；微网物理模型；机组完整启动；修复与开关；节点P/Q及电压；条件非预期性；常数项与元数据。下文解释这些块，不需要先理解矩阵每一列的手工编号。

### 4.1 先建立统一时间映射

功率与SOC使用全部96时段；启动候选、充放电模式和开关事件使用各自网格，并映射到当前t。区分这些网格是计算量控制，不是把24小时模型压成几个展示时段。启动轮廓系数将每个候选启动时刻映射为96时段辅助需求、在线状态和可发电上限。

### 4.2 变量块代表什么

| 变量名 | 默认形状 | 单位/用途 |
|---|---|---|
| `battery_charge`、`battery_discharge` | 情景×3×96 | MW，微网储能充放电 |
| `energy` | 情景×3×97 | MWh，区间边界状态 |
| `battery_mode` | 情景×3×模式数 | 二进制，防止同一时刻同时充放电 |
| `pv_used`、`dg_power` | 情景×3×96 | MW，可利用PV及可控电源 |
| `inverter_q` | 情景×3×96 | Mvar，PV/储能逆变器无功 |
| `served_critical`、`served_general` | 情景×6×96 | MW，实际恢复需求而非给定需求 |
| `target_start` | 情景×启动候选数 | 二进制，一次完整启动的起点 |
| `target_power`、`target_q` | 情景×96 | MW/Mvar，被恢复机组发电 |
| `switch_A`、`switch_B` | 情景×开关事件数 | 二进制，修复后是否接入 |
| `flow_p`、`flow_q` | 情景×6×96 | MW/Mvar，有向支路潮流 |
| `voltage_sq` | 情景×6×96 | 电压标幺值平方 |
| `grid_p`、`grid_q` | 情景×96 | MW/Mvar，初始外部电源调用 |

### 4.3 目标函数：恢复损失与资源费用必须在同一尺度

失供电费用写成“全部需求的损失常数−已恢复负荷避免的损失”。因此已恢复量的线性系数为负，但完整目标仍含常数，不是负费用奖励。再加可控电源燃料、机组启动/燃料、储能吞吐、外部购电及队伍费用，按情景概率求期望。

所有电量项含 `dt`；一次性启动费用不再乘dt。关键与一般负荷损失区分，但受保护的微网关键负荷不是靠大惩罚保障，而是直接固定供电到需求值。

### 4.4 储能块：跨期可行性与末端可持续性

每个情景和微网都满足能量递推、能量上下界、充/放电上界及模式互斥。初始能量由SOC固定，末端能量至少达到备用要求。现在上送会降低后续可用能量；中午PV可充电，但功率和逆变器容量有限。正是这组约束使24小时轨迹与96个独立单时段域不同。

### 4.5 机组块：选择启动后，整个辅助轮廓都要供应

每个情景最多选一个启动候选。辅助负荷由“候选启动×预先构造的阶段轮廓”决定，并放进T0节点的P/Q平衡；启动尚未完成时机组不能发电。完成后仍有最小/最大出力、爬坡和无功能力约束。不存在“只要y=1就自动提供满额恢复电源”的跳跃。

`branch='start'`要求当前候选启动；`branch='wait'`禁止当前候选，但保留未来候选；`branch='free'`允许不启动或选择任何候选。等待不是永久禁止启动，因而D比较的是当前动作及其后续最优续期。

### 4.6 抢修—拓扑块：修好是允许合闸，不是必须合闸

A/B恢复开关只能在对应情景已维修完成后为1，并保持恢复开关单调。B合闸时弱L0退出，避免两条并联线路构成未建模环网。A断开时第三个微网作为局部孤岛，仍需满足它本地的关键负荷与能量约束。

### 4.7 网络块：净交付量由网络守恒决定

各节点有功/无功平衡把TSO、DSO和MGO真正耦合起来。固定功率因数负荷与启动辅助功率都有无功需求。线路开时P/Q为0，关时有容量和线性电压降约束；视在功率内接多边形控制容量，参考节点电压固定。

向上功率的正确表达是 `−(flow_p[L0]+flow_p[B])`，不是三个微网发电相加。微网还要供本地负荷、充电、送往其他微网和配网；这些机会成本通过同一网络模型自动结算。

### 4.8 信息块：条件非预期性

在每个t按真实巡检结束历史分组，组内当前控制一致；组间只在已有观测足以区分后才可分支。启动和开关二进制、储能模式与连续调度必须与各自可执行时刻的信息相容。`perfect_information`只作为预先知道全部损伤的理想参照，不是可以在灾后真实执行的算法。

## 5. solution.py与experiments.py：把向量还原为研究结论

`extract_solution`根据 `var_indices`恢复各物理量的形状和单位，并从支路潮流计算净接口支撑。通过概率加权得到期望费用、恢复电量、EENS和启动概率；情景原始曲线仍保留，避免仅看均值掩盖重损情景。

实验模块遍历候选策略，为每个策略保存可行代价与下界。最小的可行上界对应当前最好候选，所有策略下界的最小值构成整个有限菜单的有效下界。某个策略超时并不自动失去成为真正最优的可能；只有其下界已经超过当前最好可行值，才可据界排除。

| 实验函数/代码块 | 具体作用 | 为什么需要它 |
|---|---|---|
| `jsonable` | NumPy数组转列表，非有限数转JSON的null | 保证输出为标准JSON；不可行代价不假装成某个巨大有限数 |
| `save_json` | 建目录、UTF-8写入、拒绝NaN | 中文可读，并阻止无效数悄悄进入结果文件 |
| `_aggregate` | 从候选策略集合计算有限菜单最优值上下界 | 每个策略MILP限时，菜单层也必须保留不确定区间 |
| `run_experiment`的`calculate` | 建模→求解→校核→checkpoint | 每次求解都有原始解和状态，可以定位具体策略的失败 |
| 当前分支复用 | 自由模型候选恰好满足条件分支时复用 | 避免重复求解；自由模型下界仍是条件子集的有效下界 |
| 分支汇总 | 分别汇总start/wait后计算D区间 | 比较同一菜单、同一续期，而非只比较两个随意候选 |
| 固定队伍参照 | 复用A_11等已求策略的结果 | 对比队伍信息适应性；不重复制造一套约束不同的基线 |
| 禁反送基线 | 同菜单增加主配接口不允许向上反送 | 衡量上送协同带来的改善，其他资源与目标一致 |
| `export_series` | 导出接口恢复长表与微网调度长表 | Excel可逐情景、逐时刻复核，不只得到一张图片 |

检查点文件中的x与该次策略/分支配置对应，不能拿另一个拓扑或另一个时间分辨率的x直接调用提取函数。元数据中的动作映射是解释向量所必需的。

### 5.1 D值为什么需要区间

若启动分支最优值在 `[L_start,U_start]`，等待分支在 `[L_wait,U_wait]`，则：

```text
D ∈ [L_wait − U_start, U_wait − L_start]
```

区间全为正才支持“现在启动更优”，全为负才支持“等待更优”；跨0时只能说明求解精度下不能确认。若当前启动不可行、等待可行，则直接报告当前动作不可行，不把无穷大差值画成普通D值。若两个分支都无可行候选，应先诊断约束，不能形成价值判断。

### 5.2 对照组应保持什么一致

所有用于价值比较的组都应使用相同资源、需求、费用、终端SOC及信息可得规则，除明确比较的机制外不额外赠送资源。有限策略、固定次序、完美信息和禁止上送等对照分别回答不同问题；没有运行的对照不能在结果表里填入假设数值。

## 6. validation.py：先证实这是一条可行轨迹

`validate_solution(model, result, cfg, tolerance)`直接读求解器原始x，而非读取舍入后的CSV，避免舍入误差造成误判。先检查是否存在有限值的完整候选，再进行两层校核。

第一层覆盖全部矩阵行和变量：下/上界违反量、整数性、目标函数含常数项的重算一致性。第二层按物理意义独立检查：SOC递推、充放电互斥、微网受保护关键负荷、一次启动/当前分支、启动完成前禁止发电、维修前禁止合闸、恢复开关单调和按真实观测分组的连续控制非预期性。

报告 `passed=True`表示本离散线性模型内满足约束，不表示AC暂态已验证，不表示所有工程动作可执行，也不表示最优性已证明。可行性与最优性是两项不同报告。

## 7. capability.py：投影图背后仍是一条完整24小时轨迹

### 7.1 `interface_trajectories`：唯一接口方向定义

从全局x抽取各情景、各时刻的向上P/Q。所有投影、分解和出图共同使用这个方向，避免某张图正值表示上送而另一张表示购电。

### 7.2 `compute_capability`：方向支持函数

先固定离散方案，再选几个展示时刻。对每个时刻和方向 `(cosθ,sinθ)`最大化接口P/Q的方向投影。每次LP仍保留全部96时段、全部情景的SOC、负荷、网络和条件非预期性，而不是只优化被展示的时刻。

每个求得的边界点保存完整高维可行见证。已认证点的凸包是当前条件凸域的内近似；支持半空间交集是外近似。有限方向通常不能精确重建边界，增大方向数只提高二维图精度，不缩短或增加模型时域。

当前域还带有整个系统的约束，因此应称“固定离散方案下、系统条件化的接口域”，不能称独立于主网/负荷状态的微网固有最大能力域。不同离散方案的域并集通常非凸。

### 7.3 `_extract_witness`：边界点的可实施凭据

保存完整上送轨迹、三微网充放电/PV/DG/SOC和恢复负荷，以及其费用和残差。这样一张P–Q多边形中的点可以追溯到原资源调度，避免只画外形却没有分解证据。

### 7.4 `decompose_trajectory`：固定整条轨迹再求内部指令

输入不是单个P/Q点，而是所有情景×所有时段的接口轨迹。函数把每个接口值作为等式加入同一条件LP，按原费用求最低成本分解。若固定P与Q都可行，输出资源见证和接口跟踪最大偏差；若只固定P，则只证明存在某种无功延拓，不能把它写成给定P/Q均可执行。

“每个时刻分别能找到资源分解”不等于“同一组资源能连续执行整条轨迹”。本函数用全时域等式和SOC将这个差异显式检验。

### 7.5 保存哪些文件

`capability.json`保存域切片、支持方向、轨迹见证和分解报告；`high_dimensional_witnesses.npz`保存对应的完整x，便于再验证。`.npz`是压缩数值数组，JSON负责可读解释；不要编辑图中一个点后继续沿用原分解证书。

## 8. plotting.py：图应回答什么问题

所有图都从求解后的 `solution.json`等结果读数，不使用手工假设的恢复曲线替代优化结果。主要图及读法如下。

| 图 | 横/纵轴与重点 | 证明范围 |
|---|---|---|
| 24小时支撑与SOC | 时间、MW和SOC；看启动消耗与后续回补 | 完整跨期资源使用及储备 |
| 恢复与未供电面积 | 需求/供电MW、累计MWh | 韧性恢复绩效，不只是启动成功 |
| 巡检抢修甘特 | 旅行/巡检/维修、情景、时间 | 物理任务顺序及观测发生时间 |
| 信息等价类 | 时刻与场景分组 | 何时允许策略分叉，是否提前获知损伤 |
| 机组启动/接替 | 辅助功率、在线出力、时刻 | 连续启动支撑及供能接替 |
| P–Q条件切片 | 接口MW/Mvar、展示时刻 | 某固定方案的投影，不是可任意拼接的轨迹集合 |
| D分支比较 | 费用与上下界 | 是否能确认当前启动/等待更优 |

SVG保留矢量线条/文字，适合论文或PPT进一步编辑；PNG便于快速浏览，PDF便于排版。图中的“期望”是情景概率加权，不代表某一个实际情景轨迹。

## 9. rolling.py：实际观测后的滚动回放

主实验是在t=0优化一棵完整的因果情景树；滚动模块则确实在后续时刻调用求解器重算。二者不是一回事。`run_rolling_replay`沿选定真实情景执行，在默认0.5、1、1.5、2、4、8、12、18h等时刻，按已经完成的巡检更新信息，并优化未执行未来。

### 9.1 输入、输出与固定边界

输入为参数、已选队伍策略、该策略的初始模型/可行解，以及实际情景ID（CLI默认HH）。真实情景仅用于环境产生当时能观察的损伤与执行轨迹；重求解只能接收截至当前的观测历史，不能直接获得剩余隐含损伤。

终点一直是原始24h。到18h时只剩6h未来，而不是重新得到一个24h储能周期。已经执行的动作和当前SOC必须继承。当前实现固定原队伍策略，不在每一轮重新比较8条路线，更不撤销已经开始的维修。它检验观测驱动的电力调度重优化，不冒充完整多队伍在线路径重规划。

| 函数/分块 | 方法 | 作用 |
|---|---|---|
| `_scenario_index` | 按情景ID映射当前数组行 | 过滤情景后避免误用旧行号 |
| `_transfer_plan` | 按ID映射上一轮完整计划 | 继续可行分支及失败回退，不重造指令 |
| `_lock_executed_prefix` | 连续动作锁`t<now`，能量状态锁`t<=now` | 当前SOC来自真实执行；不能重写历史充电 |
| 启动/模式/开关锁定 | 根据各动作网格起点锁定过去及已开始块 | 小时电池模式已开始即不能中途修改 |
| 后验筛选 | 删除与当前观测不一致的情景，剩余概率归一化 | 只利用已经发生的信息 |
| 重算与回退 | 求解+校核；若失败则验证并继续上一轮剩余计划 | 不因本轮求解时限而编造执行曲线 |
| 最终实际分支 | 从最后因果计划提取实际路径并全24h校核 | 不是对真实情景重新做完美信息优化 |

动作网格沿用初始模型，以免过滤情景后事件网格改变，导致历史开关列号/时间错位。前缀固定只允许容差内数值噪声修正，明显的边界或整数偏离会报错，而不是自动裁剪成另一条物理轨迹。

### 9.2 后验与成本该怎样解释

例如A_10的HH路径在1h知道A重伤后，后验只剩HL/HH；2h知道B重伤后，只剩HH。程序仍从原模型继承0—当前时刻已执行动作，因此“知道HH后”的续期优化不能改写0h储能决策。

每轮费用记录为给定历史和当前后验下的**全时域条件期望费用**，其中包含历史成本。不同轮次的概率和历史条件变化，不能只因费用下降就声称算法取得了同口径改进。需要比较动作价值时，应在同一轮、同一历史与后验下设置start/wait条件分支。

`round_*.json`逐轮保存观测、后验、动作、SOC、锁定数量、求解状态及校核；`rolling_rounds.csv`供表格查看；`rolling_replay.json`汇总完整回放；`executed_solution.json`是沿实际路径执行的24小时曲线。`fallback_count`大于0表示某轮沿用旧计划，应如实报告。

## 11. 常见问题定位

| 现象 | 优先检查 | 不应采用的处理 |
|---|---|---|
| 找不到可行解 | 受保护负荷、初始储能、本地电源、末端SOC、启动分支 | 直接把负荷全部设成可切除以掩盖问题 |
| 启动分支不可行 | 辅助功率峰值、联络线容量、无功/电压、初始SOC | 仅按总辅助电量认定可启动 |
| 等待更优 | 费用项、恢复机会成本、未来PV、末端储备 | 因与预期不同而改动结果数值 |
| 求解超时 | 每策略时限、整数网格、候选策略数量、求解上下界 | 不报告间隙直接声称全局最优 |
| 界面域很小或退化 | 固定方案、启动/负荷约束、Q需求、展示时刻 | 画出更大的无证据能力多边形 |
| 二维点能取但拼接不可行 | 跨期SOC、充放电模式、终端要求 | 把单时刻投影当作轨迹笛卡尔积 |
| 图看起来恢复有反复 | 是否允许连续负荷重新分配、需求本身变化 | 未加单调负荷约束却声称绝不二次失电 |

阅读代码时先问“这个量是已知参数、隐含真值、已观察信息还是决策变量”，再问它的单位和时间索引。这个顺序能避免多数恢复研究中的因果性与跨期耦合错误。

## 12. 用最小脚本看清“参数→模型→结果”的实际调用

下面只演示一条队伍策略的自由动作求解，以便理解API；完整菜单和D比较请用正式实验入口。保存为代码包根目录的 `understand_pipeline.py`，安装本项目后执行。

```python
from pathlib import Path
from tdm_restore.config import load_config
from tdm_restore.crew import enumerate_policies
from tdm_restore.model import build_model
from tdm_restore.linear import solve
from tdm_restore.validation import validate_solution
from tdm_restore.solution import extract_solution
from tdm_restore.experiments import save_json, export_series
from tdm_restore.plotting import plot_all

# 1 参数；也可传入自己的JSON路径。
cfg = load_config("configs/demo_24h.json")
# 2 选择候选策略；A_10为先巡A、轻伤先修A、重伤先去B。
policy = next(p for p in enumerate_policies(cfg) if p["id"] == "A_10")
# 3 建立全部96时段和4情景的稀疏模型。
model = build_model(cfg, policy, branch="free", information="causal")
# 4 求解，保留原始x、上下界和状态。
result = solve(model, cfg["solver"])
# 5 校核，不能因为求解器返回数值就直接出结论。
audit = validate_solution(model, result, cfg)
if not audit["passed"]:
    raise RuntimeError(audit)
# 6 提取有单位的结果并保存。
solution = extract_solution(model, result, cfg)
out = Path("results/understand_pipeline")
save_json(out / "config_resolved.json", cfg)
save_json(out / "solution.json", solution)
save_json(out / "validation.json", audit)
export_series(solution, out)
# 7 由实际时序生成论文图，仍是完整24小时。
plot_all(solution, out / "figures")
```

这个脚本没有比较其他策略，没有计算D，也没有给出能力域，因此它的结果不能替代完整实验。它的作用是把每个模块的调用关系直观呈现出来。

## 13. 入口、数据导入与测试文件

`cli.py`负责解析参数并调用 `run_experiment`。`--branches none`只求free；`--capability`增加全时域条件域；`--baselines`增加同菜单禁上送实验；`--rolling`在主实验后读取被选方案的checkpoint继续回放。`--write-config`只导出参数后返回，不启动求解。`__main__.py`允许 `python -m tdm_restore`，包安装后的命令 `tdm-restore`使用相同入口。

`scripts/run_demo.py`只定位本地src并调用正式CLI，防止另写一套示例逻辑与正式模型不一致。`scripts/import_profiles.py`依次检查时间网格、CSV列、数据行数、每个数值、时间起点顺序，再把“时段×设备”的表转成“设备×时段”的数组，调用正式配置检查后导出完整JSON。这个脚本只导入数据，不求解。

| `test_config.py` | 24h网格、概率/效率/SOC合法性、配置独立性、时间网格不跳过辅助功率峰值 |
| `test_crew.py` | 单队伍任务不重叠、先巡后修、同已知历史不能采取不同队伍行为 |
| `test_linear.py` | 固定离散状态后不出现分数容量、跨期SOC仍保留、单点可行但拼接不可行会被拒绝、求解容差不能抹去有效下界 |
| `test_validation.py` | 未观测损伤时提前分叉必须失败、合法观测后可分叉、分数二进制和无候选不能通过 |
| `test_experiments.py` | 菜单下界必须覆盖全部候选，已证不可行候选的界处理正确 |
| `test_full_model.py` | 真正96时段4情景MILP可行候选、保护负荷、SOC、费用重算、恢复电量与EENS守恒 |

测试命令见README。集成测试本身会运行一个完整24h MILP，其耗时不同于纯参数测试。测试通过也只支持当前实现边界，不证明新颖性或工程暂态安全。

## 14. sensitivity.py与run_sensitivity.py：真实扫描D，而不是手绘阈值

单个算例只能回答该组条件下的当前动作。`run_sensitivity`对指定alpha/SOC参数点逐个重新调用完整实验，保留同一菜单、24小时终点、负荷、设备和费用，仅改变初始支撑和SOC。默认扫描alpha为0、0.5、1，三个微网共同SOC为0.7；这与主示例各微网SOC略有不同，必须按解析配置解释。

| 函数/代码块 | 负责的事情 |
|---|---|
| `_parameter_fingerprint` | 排除明确扫描量和纯求解设置，检查其他物理条件是否一致 |
| `_menu_ids` | 从真实求解记录读取所用策略集合，防止混用不同菜单 |
| `_derive_decision` | 由两分支上/下界重算D区间，区分已证不可行、无候选、界不足与同号偏好 |
| `_read_case` | 读取已有结果的真实配置、SOC向量、菜单和分支证据 |
| `summarize_cases` | 只汇总已有结果并画D区间/参数图，不追加求解 |
| `run_sensitivity` | 复制基础配置、改变参数、校验、计算或复用严格相同的旧结果 |
| `scripts/run_sensitivity.py` | 参数列表/点列表解析，提供dry-run、真实扫描和已有目录汇总入口 |

`--dry-run`只校验扫描计划；`--summarize`只汇总已有目录；真正扫描才求解多个MILP。读取失败与求解失败逐点记录，不能把缺失点填成D=0。不同菜单或其余物理条件不一致时，不把各点连成同一条临界边界。

有限参数采样只给出被计算点的符号与区间；两个点符号不同仍不能证明唯一临界值，也不能保证D单调。需要进一步局部加密并收紧求解界，才可报告一个有数值证据的切换区间。主示例与外部支撑示例的结果以各自输出目录为准，本导读不预写其数值或符号。
